# 术语与计数口径

> **本文件是仓库内所有数字表述的唯一口径来源。** 任何文档（README、docs、模块 SKILL、代码里的用户可见文案）写到下列数字时，以本文件为准。
>
> 背景：这些数字曾出现"同一处 24、另一处 25"的混用，以及"六态"实际 8 个取值的命名遗留。外部审阅者把它当作质量信号，所以这里把口径摊开写死。

## 1. 模块

**模块** = `assets/modules/<slug>/` 下的一个目录（含 `module.yaml`、`SKILL.md`、`prompts/`、`rules/`、`fallback.md`）。`_shared/` 是公共片段，**不是**模块。

模块总数 **25**。同一个 25 有三种正确切法，彼此不冲突，但**不能混着说**。

### 1.1 按职能（这个模块干什么）

| 类别 | 数量 | 成员 |
|---|---|---|
| 专用调查方向 | 23 | 除下面两个之外的全部模块 |
| 通用兜底 | 1 | `generic-investigation` |
| 交付构建器 | 1 | `deliverable` |
| **合计** | **25** | |

> `deliverable` 是**交付构建器**，不是调查方向；`generic-investigation` 是**兜底**，没有专用方向时用它。把这两类混称"调查方向"是错的。

### 1.2 按来源 provenance（谁写的）

来源写在每个 `module.yaml` 的 `provenance` 字段里，取值 `human` / `agent`。规则见 [`模块作者指南.md`](./模块作者指南.md)。

| `origin` | 数量 | 作者 | 成员 |
|---|---|---|---|
| `human` | 1 | `60777flowers` | `investment-map` |
| `agent` | 24 | `ai-draft` | 其余全部模块 |
| **合计** | **25** | | |

### 1.3 按成熟度（能不能用）

| 层级 | 数量 | 成员 | 备注 |
|---|---|---|---|
| 人工实现 | 1 | `investment-map` | 唯一 `0.2.0`；对抗式复核；源自实战 skill v7 |
| R1 框架骨架 | 4 | `entity-resolution`、`ownership-chain`、`deliverable`、`generic-investigation` | 为跑通端到端而写，方法论待补 |
| 通用初稿 | 20 | 其余专用调查方向 | 按公开信息最佳实践编写 |
| **合计** | **25** | | |

> **关键关系**：1.3 中"框架骨架 4 + 通用初稿 20 = 24"，这 24 个的 `provenance.origin` **全部是 `agent`**。也就是说 1.3 是对 1.2 中 `agent` 那 24 个的再细分，不是另一套来源口径。

### 1.4 三个"24"——最容易出错的地方

数值相同、含义完全不同：

| 说法 | 含义 | 换算法 | 出现场景 |
|---|---|---|---|
| 24 个 AI 初稿 | 25 − 1 个人工实现 | 4 骨架 + 20 初稿 | 讲来源、讲成熟度 |
| 24 个调查类模块 | 25 − 1 个交付构建器 | 23 专用 + 1 通用兜底 | 讲职能 |
| deep 预设 24 个模块 | 预设**启用**数 | 25 − 1 通用兜底（deep 不含 generic） | 讲预设 |

> **写作规则：禁止裸写"24 个模块""24 个方向""24 个内置"。**
> 必须带限定语，例如："24 个 AI 初稿""24 个调查类模块""deep 预设启用的 24 个模块"。
> 同理，裸写"25"也要说明是模块总数。

## 2. 预设

**预设** = `assets/playbooks/*.yaml`，共 **5 个**：`skill-only`、`quick`、`standard`、`deep`、`generic`。

| 预设 | 启用模块数 | 说明 |
|---|---|---|
| `skill-only` | 4 | 旧资产闭环 |
| `quick` | 10 | 48 小时初筛 |
| `standard` | 18 | 标准尽调前调查（默认） |
| `deep` | 24 | 全模块（不含 `generic-investigation`） |
| `generic` | 3 | 通用调查 |

> 这些是**启用数**，不是库存数。不要与模块总数 25 做加减，也不要把"deep 24"当成模块总数。

## 4. 状态字段（旧称"六态"，实际 8 个取值）

**历史命名遗留**：契约与部分文档沿用"六态"这个叫法，但实际枚举了 **8 个取值**：

`found` · `not_disclosed_after_search` · `lower_bound` · `pending_dd` · `conflict` · `not_applicable` · `not_reviewed` · `estimated`

> **写作规则**：首次出现写"状态字段（文档旧称「六态」，实际 8 个取值）"，之后可简称"状态字段"。
>
> **适用范围**：
> - **对外文档与交付物文案**（README、工作簿"说明"页、QA 与签发记录、模块作者指南）不要单独写"六态"——外部读者会去数，数出 8 个，然后怀疑整份文档；
> - **模块方法论文件**（`assets/modules/*/SKILL.md`、`prompts/`、`rules/`）统一沿用契约旧称「六态」，定义只在 `assets/modules/_shared/_system.md` 与 [`实现契约.md`](./实现契约.md) §3.4 两处，避免上百处同义改写引入新错。

## 6. 校验

```powershell
node tools/check-docs.mjs   # 目录↔标题同步、锚点可解析、裸写"24"检测
node tools/check.mjs        # 语法 + 资产 + 预设编译 + 文档校验
npm run check:docs          # 等价于上一条 check-docs
```

`check-docs.mjs` 会做三件事：
1. README 的"目录"与正文 `## N.` 标题逐条对应（编号连续、标题一致、锚点可解析）；
2. 正文里禁止出现裸写 `24 个模块` / `24 个方向` / `24 个内置` / `25 个`（后接歧义语境）；
3. 出现"六态"时必须同句或同段出现"8 个取值"的说明。
