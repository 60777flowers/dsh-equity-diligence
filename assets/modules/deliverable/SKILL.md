# 报告与附表（deliverable）

> 模块状态：`draft`。方法论可执行、有门与 rubric，**尚未经过金融专家评审**。
> 不得在交付物中标注 `stable` 或“专家已审”。

## 1. 一句话目标

把已完成的底稿**构建**成一套可交付包：管理层摘要、综合工作簿、7+N 投资版图专项、
工作底稿包、证据快照、资料请求清单、QA 与签发记录。

### 1.1 这是构建器，不是检索模块

- 本模块**不检索、不补事实**：没有底稿支撑的内容只能进“待核”或“资料请求”。
- 报告中的每个数字、每个结论必须能回指 `claimId` + `artifactId` + `revision` + `contentHash`。
- **报告不得创造底稿之外的新事实**；措辞可以改写，事实不能新增。
- 工具可打开证据快照核对引文，但不得引入新来源、新的公司事实。

### 1.2 本模块不做

- 不做主体识别、股权穿透、投资版图与红旗判断（各由上游模块产出）。
- 不做投资建议、不做估值结论、不代替 IC 决策。
- 不修改上游底稿；发现错误走 `openQuestions` 与 `equity_review`。

| 序号 | 产物 | 内容 | 状态 |
|---|---|---|---|
| 01 | `01_管理层摘要.md` | 5–10 条结论，每条“事实→影响→证据强度→materiality→下一步” | 必出 |
| 02 | `02_综合尽调工作簿.xlsx` | 11 个页签：目录/摘要/主体股权/业务技术/财务/风险/待核/资料请求/来源索引/底稿索引/体检 | 必出 |

| 04 | `04_工作底稿/<moduleId>/workpaper.md` | 每个模块一页：口径、来源、字段、开放问题 | 必出 |
| 05 | `05_证据快照/` | 关键证据原文快照，按 `rawHash` 命名 | 必出 |
| — | `manifest.json` | 文件清单 + `sha256` + 大小 + 类型 | 必出 |

规则：

- 文件名、目录名固定，不得改名或增减层级；`manifest.json` 必须覆盖全部产物。
- 同一项目重跑时覆盖同名文件，旧版本进 `.equity/` 历史，不散落在 `05_交付/`。
- PDF 可选，先出 Markdown；PDF 不得与 MD 内容不一致。

## 4. 管理层摘要（5–10 条）

### 4.1 每条五段式

1. **事实**：可核的客观陈述，带数字与口径，不写形容词。
2. **影响**：对交易、控制、经营或合规的影响方向，不写投资建议。
3. **证据强度**：A/B/C/D 级 + 独立来源数 + 是否有冲突。
4. **materiality**：`material`/`attention`/`context`，与红旗级别一致。
5. **下一步**：需核什么、向谁要、何时要。

每条必须挂 `claimId` 与 `artifactId`；缺任一项不得进摘要。

### 4.2 条数与排序

- 5–10 条：少于 5 条说明调查不足，多于 10 条说明没有取舍。
- 排序：`material` 红旗与控制结论优先，其次财务与业务，最后背景。
- 重大风险（`red-flags` 的 `material`）必须出现在前三条之一。
- 不得把同一事实拆成多条凑数，也不得把两条不同事实合并成一条。

### 4.3 摘要禁止

- 不写“建议投资/不建议投资/估值偏低”等结论。
- 不写没有底稿支撑的判断；不确定的进“待核”章节。
- 不把 `estimated` 写成确定值，必须标“估算 + 方法”。
- 不写“据了解/业内普遍/大概”。

## 5. 综合工作簿（11 页签）

| 页签 | 内容 | 数据来源 |
|---|---|---|
| `00_目录` | 章节、sheet、说明、数据截至日 | `manifest` + 运行信息 |
| `01_执行摘要` | 序号 / 事实 / 影响 / 证据强度 / materiality / 下一步 / claimId / artifactId | `summaryFindings` |
| `02_主体与股权` | 主体、股东、控制链、特殊权利 | `company.identity`、`ownership.chain` |
| `03_业务与技术` | 产品、客户、供应链、技术来源、资质 | 相关模块 |
| `04_财务` | 财年分区财务摘要与勾稽 | `financials.public` |
| `05_风险` | 红旗、触发器结果、待核 | `risk.redflags` |
| `06_待核清单` | 主题 / 问题 / 为什么重要 / 优先级 / 来源 | 各模块 `openQuestions` |
| `07_资料请求` | 编号 / 主题 / 问题 / 为什么 / 优先级 / 负责人 / 状态 | `dd.request_list` |
| `08_来源索引` | evidenceId / 标题 / URL / 类型 / 权威度 / 核验状态 / 截至日 / 抓取时间 / rawHash | 各模块 evidence |
| `09_模块底稿索引` | artifactId / 类型 / 主体 / 分区 / 状态 / revision / contentHash / asOf / 证据数 / claim 数 | 底稿索引 |
| `10_体检单` | 检查项 / 结果 / 说明 | 本模块 QA |

格式规则（参考机构级工作簿惯例）：

- 每 sheet 第 1 行标题、第 2 行表头、第 3 行起数据；冻结表头、自动筛选、列宽适配、自动换行。
- 数字右对齐、百分比一位小数、金额标币种与单位、年份用文本避免千分位。
- 空值显示六态文案，不留空；`02`–`05` 字段行格式为 `字段 / 值 / 状态 / 证据`。
- 不额外加装饰性图表；颜色只用海军蓝/浅蓝/浅灰。
- `cellMap` 每条 pin：`location`、`claimId`、`artifactId`、`artifactRevision`、`artifactContentHash`、`value`、`evidenceIds`。

## 6. 7+N 投资版图专项

### 6.1 结构（强制）

| 编号 | 工作表 | 说明 |
|---|---|---|
| 1 | `1-直接投资` | 固定 |
| 2 | `2-合作基金-GP` | 固定；只有一个 GP 平台时可括号冠平台名 |
| 3 | `3-合作基金-主导LP` | 固定 |
| 4 | `4-合作基金-财务LP` | 固定 |
| 5 | `5-海外平台` | 固定 |
| 6 | `6-合资公司` | 固定 |
| 7 | `7-国内基地` | 固定 |
| 8–10 | `8/9/10-<代表人物>家族` | 动态，≤3 张，按影响排序 |
| — | `说明` | 口径、待关注清单、数据来源、整理日期 |

- 不得合并七张固定表、不得拆表、不得漏表、不得改编号。
- 家族表超过 3 个群体时取影响前 3，其余写入说明页待关注清单。

### 6.2 行粒度与列

- 一行 = 一个（平台路径 × 被投实体）对；同一实体多路径时在每张涉及分表各占一行。
- 列结构：平台五列（平台/主体、类型/角色、股权结构/出资、战投定位/协同方向、时间/备注）
  + 调研列；清理版删除“调查时间/审核状态/数据质量说明/结果 JSON 文件”四列，24 列变 20 列。
- 列名与顺序不得重命名、换序、合并、增删；调研列名与汇总表逐字一致（去后缀）。
- 标绿只由确定性规则完成（合作潜力、投资合作评估两列的固定词表），不由人工判断。
- 值语义检查：比例列必须是百分比，股东数必须是数字，毛利率必须是百分比，融资金额必须带币种。

## 7. 底稿包与证据快照

- `04_工作底稿/<moduleId>/workpaper.md`：模块目标、输入、口径、关键字段、来源清单、开放问题、分数。
- `05_证据快照/`：以 `rawHash` 命名的原文快照，与 `evidence.snapshotPath` 一致。
- 底稿包只读引用底稿，不复制成“摘要版事实”；如需摘录，必须保留 `claimId`。
- 证据快照缺失时，对应结论在报告中降级为 `pending_dd`。

## 8. 资料请求清单（`dd.request_list`）

- 每条：`id`、`topic`、`question`、`why`、`priority`（high/medium/low）、`owner`、`status`。
- 来源：各模块 `openQuestions` + `red-flags` 的 `ddRequests`，去重后合并。
- 一条请求只问一件事，必须可执行（向谁要、要什么材料、用于核什么）。
- 不把“继续关注”“补充调查”这类空话写成请求。

## 9. QA（阻断 vs 非阻断）

### 9.1 阻断项（必须为 0 才能签发）

| 检查 | 判据 |
|---|---|
| 摘要存在 | `01_管理层摘要.md` 缺失即阻断 |
| material 证据 | `material` claim 无 `supports` 证据 |
| 摘要血缘 | 摘要结论引用不存在的 `claimId` |
| 数字一致性 | 报告数字与底稿 claim 不一致 |
| 同口径矛盾 | 同一指标在不同页签口径/数值冲突 |
| 未处理 stale | 上游 `stale`/`rejected` 未重跑或未说明 |
| 血缘 pin | 摘要结论所引 claim 缺 `artifactId`/`artifactRevision`/`artifactContentHash` |
| 工作簿结构 | 综合工作簿缺 `00_目录`–`10_体检单` 任一页签 |
| 7+N 结构 | 缺固定表，或清理版前 20 列表头与契约不逐字一致 |
| 公式错误 | 工作簿存在 `#REF!`/`#N/A`/`#VALUE!`/`#DIV/0!` |
| 表头质量 | 表头为空或重复 |
| 摘要条数 | 少于 5 条或多于 10 条 |
| 红旗失联 | `material` 红旗未进摘要首页 |

### 9.2 非阻断项（记录并提示）

- 覆盖不足、上下游证据等级偏低、`pending_dd` 字段偏多。
- 触发器 `insufficient` 较多、境外层未穿透、家族平台“疑似未证实”。
- 格式告警（列宽、批注缺失、PDF 未生成）。

### 9.3 QA 输出

- `qa.blocking`、`qa.warnings`、`qa.passed` 三字段；`passed=true` 仅当阻断项为 0。
- 体检页签列出每条检查的 id、结果、定位、修复建议。
- 阻断项不得用“已人工确认”一行带过；必须修复或明确降级并留痕。

## 10. 签发

- `signoff.preparedBy`：构建者（Agent 或人工）；`proposedAt` 写提交复核时间。
- `signoff.reviewedBy`：复核人；`approvedBy`：签发人。
- **Agent 只能 `proposeReview`**，不得自行填写 `approvedBy` 或 `signedAt`。
- 签发前必须 `qa.passed=true`；签发后修改任何数字需重跑 QA 并重新提交复核。
- 签发记录写入 `QA与签发记录.md`，与 `manifest.json` 一并交付。

## 11. 不创造新事实的机制

1. **单一事实源**：所有事实来自 claims/evidence；报告只做选取、排序、措辞。
2. **pin 三件套**：`artifactId` + `revision` + `contentHash`；任一变更触发下游 `stale`。
3. **措辞不改事实**：允许压缩、合并同类项，不允许新增数字、主体、日期。
4. **无源即待核**：找不到支撑的事实，进“待核”或 `dd.request_list`，不进正文。
5. **冲突不掩盖**：同一事实两个值，报告写“存在冲突 + 两个候选 + 待裁决”。
6. **估算标注**：`estimated` 必须带 `derivation`，并在报告标“估算”。

## 12. 六态与边界

本模块沿用上游八种状态（六态命名，实际八值）：

- `found`：上游已确认且有证据，可直接进报告。
- `not_disclosed_after_search`：报告写“已查未披露 + 检索范围”。
- `lower_bound`：报告写“至少”，不得写成精确值。
- `pending_dd`：进待核与资料请求，不进正文结论。
- `conflict`：报告并列候选，不擅自择一。
- `not_applicable`：报告写“不适用 + 原因”。
- `not_reviewed`：报告写“未调查”，不得写成“无”。
- `estimated`：只出现在分析型字段，必须标方法与假设。

其余规则：

- 摘要与工作簿中的每个字段沿用上游六态，不得把 `pending_dd` 写成 `found`。
- `conflict` 在报告中并列候选，不选一个“看起来合理”的。
- 本模块自身不产出 `estimated`；`gates.maxEstimatedRatio=0`。
- 报告不出现空字段；无内容写“未调查/未披露/不适用”并说明。

## 13. 常见误判

1. **摘要写成结论堆砌**：没有“影响/证据强度/下一步”，读者无法判断可信度。
2. **报告创造新事实**：为了叙事顺畅补一个数字或主体，属于严重违规。
3. **只改 Excel 不回写底稿**：交付件与底稿脱节，下次重跑即丢失。
4. **家族表超过 3 张**：违反 7+N 结构，QA 阻断。
5. **列名重命名/换序**：大规模数据错位的主要来源。
6. **手工标绿**：规则不确定，复核无法复现。
7. **红旗只进正文不进首页**：重大风险被埋没。
8. **QA 只跑结构不跑一致性**：数字对不上仍能签发。
9. **把 stale 当 verified**：上游变更未重跑，报告仍引用旧值。
10. **签发人由 Agent 代填**：越权，签发无效。

## 14. 验收要点

- `manifest.json` 覆盖全部产物，`sha256` 与文件一致。
- 摘要 5–10 条，每条五段式齐全并挂 `claimId`/`artifactId`。
- 工作簿 11 页签齐全，`cellMap` 三跳可追溯（报告→claim→evidence）。
- 7+N 表数、表名、列序、列数符合规则；多路径实体在各表均有行。
- QA 阻断项为 0；非阻断项已记录并提示。
- 签发字段完整，`approvedBy` 由人工填写。
- 报告与底稿数字逐项一致，无新增事实。

## 15. 与其他模块的关系

- 上游：全部业务模块（`all` 展开）；重点读取 `ownership.chain`、`investment.map`、`risk.redflags`。
- 下游：无（交付终点）；`equity_deliver` 工具读取本模块产出。
- 本模块不修改上游；发现错误写 `openQuestions` 并触发 `equity_review`。

## 16. 已知缺口（draft 阶段）

- PDF 生成依赖外部工具，当前先出 Markdown；PDF 版本需单独验收。
- 7+N 标绿规则词表需按部门口径维护，词表变更要重跑并记录版本。
- 家族表冠名依赖人工判定主导群体，Agent 只能给建议。
- 签发流程依赖 Web API 的 `user` 通道，工具侧只能 `proposeReview`。
