# 通用调查（generic-investigation）

> 模块状态：`draft`。方法论可执行、有门与 rubric，**尚未经过金融专家评审**。
> 不得在交付物中标注 `stable` 或“专家已审”。

## 1. 一句话目标

当没有专用模块覆盖某个问题时，对**任意公开可查问题**做一次有证据、可复核的初步调查，
输出结构化结论（`structured.findings`）与一份只由这些结论生成的报告（`document.markdown`）。

### 1.1 兜底定位

- 本模块是 skill-only / generic 预设的兜底：**不依赖脚本、不依赖子代理、不依赖额外安装**。
- 只要有 `web_search`、`web_fetch`、`equity_record` 三个工具就能跑完。
- 与专用模块重叠时，优先专用模块；本模块只做专用模块未覆盖的问题。
- 不替代 `legal.risk`、`regulatory.compliance`、`financials.public` 等有固定字段的模块。

### 1.2 不做什么

- 不给出投资建议、不判断估值高低。
- 不把分析框架当结论，不把“可能/或许/不排除”当证据。
- 不采集个人隐私、证件号、与交易无关的私生活信息。
- 不修改上游底稿，不写项目之外的文件。

## 2. 输入与前置

| 输入/参数 | 必要性 | 缺失时 |
|---|---|---|
| `company.identity` | `onMissing: degrade` | 降级运行：用已知名称检索，报告注明“主体未核验” |
| `{{params.question}}` | 有默认值 | 按默认问题执行；空问题时先拆题并在 `openQuestions` 说明 |
| `{{params.depth}}` | `quick`/`standard`/`deep` | 决定检索轮次、来源数与结论条数下限 |
| 用户追问 | 可选 | 只作拆题输入，不作事实来源 |

### 2.1 不依赖声明

- 不需要 API key、批处理脚本、子代理、外部数据库或前序模块全部完成。
- 缺 `company.identity` 时降级为“按名称调查”，不因缺输入而拒绝运行。
- 单次运行即可产出可用结果；深度由 `depth` 控制。
- 不允许要求用户先跑脚本或先启动子代理才能出结果。

### 2.2 适用与不适用

适用：

- 专项模块未覆盖的问题（如某细分市场的公开数据、某技术路线的公开进展）。
- 已有模块产出不足、需要补一条线索的场合。
- 快速预设下只需要“有没有公开信息”的初筛。

不适用：

- 有固定字段与法定口径的调查（股权、工商、财务、诉讼、合规），应走专用模块。
- 需要企业内部材料才能回答的问题，只做 `pending_dd` 记录。
- 需要建模、估值、投资判断的问题，本模块不给结论。

## 3. 检索计划（先写计划，再检索）

### 3.1 拆题

把 `question` 拆成 3–7 个可独立回答的子问题：

- 是什么：定义、主体、范围。
- 谁在做：公司、机构、人物。
- 规模与时间：金额、数量、日期，必须带口径。
- 关系：与目标公司的股权、业务、人员关系。
- 风险与争议：诉讼、处罚、负面报道。
- 缺口：公开信息查不到的部分。

拆题结果写进 `openQuestions` 或 `findings[].claim`，让读者看到“问了什么”。

### 3.2 关键词

- 中文：`[主体] [主题]`、`[主体] [主题] 公告`、`[主体] [主题] 数据`、`[主题] 监管 规定`。
- 英文：`[subject] [topic]`、`[subject] [topic] filing`、`[topic] regulation`。
- 主体名同时用全称、简称、英文名各试一次；简称结果必须回全称核验。
- 不用“内幕/爆料/独家”类词作为主检索词，避免把传闻当事实。

### 3.3 来源优先级

| 级别 | 来源 | 用途 |
|---|---|---|
| A | 公告、监管处罚、法院文书、交易所、审计报告 | 结论主证据 |
| B | 工商登记、协会备案、政府统计、官方数据库 | 交叉核验 |
| C | 公司官网、权威媒体、行业报告 | 背景与补充 |
| D | 一般媒体、自媒体、论坛 | 只作线索，不回核不进结论 |

## 4. 多轮检索协议

| 深度 | 最少轮次 | 最少独立来源 | 结论条数下限 |
|---|---|---|---|
| `quick` | 2 轮（中文 + 英文各一） | 2 | 3 |
| `standard` | 3 轮（含一次回核） | 3 | 5 |
| `deep` | 5 轮（含反证检索） | 5 | 8 |

- 每轮记录：检索词、引擎、日期、结果数、打开的关键页面、结论变化。
- 第二轮必须做**反证检索**：搜“否认/澄清/处罚/诉讼/辟谣”等反面词。
- 同一事实两种独立来源交叉；转载合并为同一 `originGroupId`。
- 打开页面后摘录原文，不以搜索摘要代替原文。
- 每轮结束更新 `sourceCoverage.queries`，记录 `outcome`（有进展/无进展/被阻断）。

## 5. 结论与证据

- 一个结论 = 一条 claim：`predicate` 明确、`value` 具体、`period.asOf` 清楚。
- 每条 claim 至少一条 `supports` 证据；`material` claim 必须 **100%** 有证据。
- 证据写 `url`、`title`、`quote`（原文片段）、`locator`、`sourceTier`、`asOf`。
- 证据不足的结论降级为 `openQuestions`，不得用“据了解/业内普遍”填充。
- 同一结论的多条证据并列；相互矛盾的证据同时保留，写 `conflict`。

### 5.1 证据强度标注

| 标注 | 含义 |
|---|---|
| A-强 | A 级来源直接表述，且与 B 级交叉一致 |
| B-中 | A 级或 B 级单一来源，未交叉 |
| C-弱 | 仅官网/媒体表述，未回原始文书 |
| D-线索 | 只有传闻或搜索结果摘要，未打开原文 |

强度只描述证据，不描述结论重要性；`materiality` 单独标注。

## 6. `not_found` 与 `search.ledger`

- 任何“查不到”的结论必须使用 `not_disclosed_after_search`，并附检索记录。
- 检索记录由系统单元 `search.ledger` 产出；本模块在 `note` 与 `openQuestions` 中引用其
  `moduleInstance` 与尝试条目（检索词、引擎、日期、结果数）。
- **没有 ledger 记录的“查不到”不得写成 `not_disclosed_after_search`**，只能写 `not_reviewed`。
- 已尝试路径要写全：查过哪些库/站、用过哪些词、筛过什么时间范围、为什么仍不足。
- 明确区分三种“没有”：

1. 确实不存在：有权威来源明示“无此记录”。
2. 已查未披露：`not_disclosed_after_search` + ledger。
3. 尚未查：`not_reviewed` + 计划。

## 7. 报告只从 claims 生成

### 7.1 生成规则

- `document.markdown` 的每一段都必须能对应到 `claims` 中的至少一条。
- 段落内引用写法：`（见 cl_xxx）`；没有 claim 支撑的句子一律删除。
- 不允许在 markdown 中出现新的数字、日期、主体、结论。
- 报告结构：问题 → 方法与来源 → 结论（按 materiality 排序）→ 待核 → 来源清单。

### 7.2 报告骨架（结构示意）

```markdown
# <主体> <主题> 初步调查
## 1. 问题
## 2. 方法与来源（检索轮次、来源级别、限制）
## 3. 结论
- <结论 1>（见 cl_xxx）
- <结论 2>（见 cl_xxx）
## 4. 待核
- <缺什么、已尝试什么、下一步>
## 5. 来源清单
- ev_xxx / 标题 / 来源级别 / 抓取日期
```

骨架只规定顺序，不预填内容；每段内容都必须有 claim 支撑。

### 7.3 禁止

- 不把分析框架写成结论（“可能”“或许”“不排除”不能替代证据）。
- 不把背景知识当检索结果；不把官网自述当第三方验证。
- 不把 `estimated` 写成确定值；估算必须带方法与假设。
- 不在 markdown 中写 claims 没有的主体、金额、日期。

## 8. 六态与边界

- `found`：至少一条 A/B 级来源直接支撑，且与另一来源不冲突。
- `not_disclosed_after_search`：有 ledger 记录，写清查过什么。
- `lower_bound`：只用于“至少/不少于”类事实。
- `pending_dd`：需企业内部材料或付费数据库才能确认。
- `conflict`：多源矛盾，保留候选与差异。
- `not_applicable`：问题本身不适用于该主体（如非上市公司无股价）。
- `not_reviewed`：未查或预算耗尽。
- `estimated`：仅分析型字段（市场规模、区间），必须带 `derivation{method,inputs,comparables,assumptions}`。
- 六态之外不新增状态；每个字段都要有 `note`。

### 8.1 字段级写法

- `findings[].confidence` 用 `high/medium/low`，与证据强度对应，不写“较高”。
- `findings[].openQuestions` 写该条结论仍缺什么，便于 `deliverable` 汇总。
- `document.markdown` 里的“待核”段必须与 `openQuestions` 一致。
- `sourceCoverage.limitations` 写检索限制（语言、付费墙、地区）。
- 所有日期写 `YYYY-MM-DD`；金额带币种；比例带口径。

## 9. 常见误判

1. **用背景知识代替检索**：模型记忆不是证据。
2. **一条来源支撑多个结论**：同一来源只能证明它明说的那一件事。
3. **官网自述当第三方验证**：只能证明“公司曾如此声明”。
4. **搜索摘要当原文**：必须打开页面摘录。
5. **无 ledger 写“未披露”**：把“没查”伪装成“没有”。
6. **markdown 与 findings 不一致**：报告出现 claims 之外的内容。
7. **把传闻写成风险**：媒体线索必须回原始文书。
8. **忽略时间口径**：旧数据当现状，未标 `asOf`。
9. **以偏概全**：单一样本推全体（如一家客户推行业需求）。
10. **过度定性**：把“存在关联”写成“存在利益输送”。

## 10. 验收要点

- `data.question` 明确，`findings` 与 claims 一一对应。
- `material` claim 证据覆盖 100%；无证据的结论已降级。
- 每条 `not_disclosed_after_search` 都能在 `search.ledger` 找到尝试。
- `document.markdown` 中每段都有 `claimId` 引用，无新增事实。
- 深度参数对应的轮次、来源数、结论条数达到下限。
- 不出现投资建议与定性结论。
- 每条结论都能回答“来源是什么、什么时候抓的、原文哪一句”。
- 报告与 findings 同源：删掉任一 claim，报告对应段落必须同步消失。

## 11. 与其他模块的关系

- 上游：`company.identity`（可降级）；不强制依赖其他模块。
- 下游：`deliverable` 可把本模块结论并入摘要与工作簿。
- 与专用模块重叠时：优先专用模块；本模块只做“专用模块未覆盖的问题”。
- 本模块不替代 `legal.risk`、`regulatory.compliance` 等有固定字段的模块。
- 与 `deliverable` 的接口：`structured.findings` 提供结论，`document.markdown` 提供叙事。
- 与 `search.ledger` 的接口：只引用，不生成；ledger 缺失时降级为 `not_reviewed`。

## 12. 已知缺口（draft 阶段）

- 拆题质量依赖问题表述；问题过于宽泛时结论会发散，需在 `openQuestions` 收敛。
- `search.ledger` 由内核系统单元产出，离线 fixture 下可能为空，此时只能写 `not_reviewed`。
- 深度参数的轮次是下限，不保证覆盖所有语言与地区。
- 报告生成依赖 claims 质量；claims 稀疏时报告会显得单薄，这是真实覆盖不足，不应美化。
