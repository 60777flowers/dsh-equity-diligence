# public-sentiment · 舆情与利益相关方

> 模块状态：**draft**。方法论未经金融专家评审，不得声称 `stable` 或"专家已审"。
> 输出底稿：`public.sentiment`（scope=company，cardinality=one，partitionKey=`_default`）。
> 一句话目标：把"外界怎么说它、谁在受影响、事情后来怎么样了"记成可追溯的事件清单，而不是情绪判断。

## 1. 回答什么问题

1. 近 `{{params.daysBack}}` 天有没有负面事件（质量、欠薪、安全、环保、财务质疑、举报）？
2. 每个事件的首次曝光时间、传播路径、当事人是否回应、后续处置如何？
3. 有没有实名举报、集体投诉、监管立案等升级信号？
4. 员工、客户、供应商、周边居民、监管、投资人分别是什么态度？
5. 整体口碑在时间窗内是改善、恶化还是平稳？
6. 哪些信息是已裁定事实、哪些只是指控、哪些只是匿名帖？

## 2. 输入、前置与降级

| 关系 | 类型 | 说明 |
|---|---|---|
| 硬输入 | `org.people` | 关键人姓名与职务，用于人物相关舆情检索 |
| 硬输入 | `business.segment` | 产品与客户，用于质量类舆情检索词 |
| 软引用 | `legal.risk` | 已进入司法程序的事件，避免重复与矛盾 |

- 降级：无 `org.people` 时只做公司层面检索，人物维度写 `pending_dd`。
- 分区：单一 artifact，`{{unit.partition}}` 恒为 `_default`。
- 时间窗：`{{params.daysBack}}`（默认 365 天）；窗口外但仍在发酵的事件必须收录并注"历史事件仍在传播"。

## 3. 检索计划

### 3.1 来源优先级

| 序 | sourceTier | 典型来源 | 用途 | authority |
|---|---|---|---|---|
| 1 | court | 人民法院公告网、开庭公告、破产公告 | 已进入司法程序的事件 | A |
| 2 | regulator | 监管通报、举报处理结果、处罚公示 | 官方定性 | A |
| 3 | announcement | 公司澄清公告、声明、年报"重大事项" | 当事人回应 | A（事实）/self_reported（定性） |
| 4 | media | 财新、界面、澎湃、证券时报、21 世纪等 | 记者核实过的报道 | B–C |
| 5 | media | 行业媒体、地方媒体 | 补充 | C |
| 6 | database | 黑猫投诉、12315 公示、投诉平台 | 消费类投诉 | C |
| 7 | media | 微信公众号、知乎、贴吧、小红书、抖音、脉脉 | 匿名与员工舆情 | D |

### 3.2 中文检索词

- `"<公司全称>" 投诉`、`"<公司全称>" 质量`、`"<公司全称>" 退货`
- `"<公司全称>" 欠薪`、`"<公司全称>" 裁员`、`"<公司全称>" 讨薪`
- `"<公司全称>" 举报`、`"<公司全称>" 造假`、`"<公司全称>" 做空`
- `"<公司全称>" 事故`、`"<公司全称>" 污染`、`"<公司全称>" 维权`
- `"<公司全称>" 声明`、`"<公司全称>" 澄清`
- `"<关键人姓名>" 负面`、`"<关键人姓名>" 纠纷`

### 3.3 英文检索词

`"<English name>" complaint`、`"<English name>" lawsuit`、`"<English name>" recall`、`"<English name>" short seller report`、`"<English name>" whistleblower`。

### 3.4 必查库与必开页面

- 综合搜索：百度、必应、谷歌（各取前几页，记录检索日期）；
- 财经媒体站内检索与公司名标签页；
- 黑猫投诉、12315 公示、消费维权平台；
- 微信公众号文章（通过搜狗微信或站内搜索）；
- 人民法院公告网与地方法院开庭公告；
- 公司官网"新闻中心"与公告"澄清"类文件。

### 3.5 检索顺序与预算

1. 综合搜索铺面（约 4 次）；
2. 重点事件回原文（约 5 次）；
3. 投诉与举报平台（约 3 次）；
4. 当事人回应（约 2 次）；
5. 利益相关方（约 3 次）。
上限见 `module.yaml` 的 `budget.toolCallsPerUnit=18`。

### 3.6 来源可得性与替代路径

| 来源 | 可得性 | 拿不到时的替代 |
|---|---|---|
| 综合搜索 | 高 | 换引擎、换关键词组合 |
| 财经媒体 | 中（部分付费墙） | 用摘要 + 其他媒体交叉，标注"仅摘要" |
| 微信公众号 | 低（需搜狗微信，收录不全） | 用转载该文的门户或行业站 |
| 脉脉 | 低（需登录） | 不强行抓取，改写 `not_reviewed` |
| 黑猫投诉 | 中 | 用 12315 公示或消费维权报道 |
| 法院公告 | 高 | 用裁判文书网或地方公告栏 |

## 4. 字段与口径

| 字段 | 结构 | 定义 | 算 `found` | 算 `not_disclosed_after_search` |
|---|---|---|---|---|
| `data.incidents[]` | `date`/`title`/`summary`/`sourceTier`/`status`/`note` | 单个事件 | 有可打开的原始页面 | 只有搜索结果标题 |
| `data.sentiment[]` | `period`/`tone`/`summary`/`note` | 分时段口碑 | 有样本与时间窗 | 样本不足 3 条 |
| `data.stakeholders[]` | `party`/`stance`/`note` | 利益相关方态度 | 有公开表态或可核事实 | 无公开信息 |

- `incidents.status` 用固定词：`发酵中`/`已回应`/`已和解`/`已判决`/`已平息`/`unknown`。
- `sourceTier` 必须与证据一致：`court`/`regulator`/`announcement`/`media`/`database`。
- `sentiment.tone` 用 `正面`/`中性`/`负面`，并在 note 写样本量与时间窗。
- `stakeholders.party` 用 `员工`/`客户`/`供应商`/`周边居民`/`监管`/`投资人`/`合作伙伴`；`stance` 用 `支持`/`中立`/`反对`/`未知`。

### 4.1 五级信息强度（硬性区分）

| 级别 | 含义 | 写法 |
|---|---|---|
| 已裁定事实 | 法院判决、监管处罚决定、官方调查结论 | 可直接陈述 |
| 监管指控 | 立案调查、处罚告知、起诉书 | 写"被指控/被立案"，不写"违法" |
| 企业自述 | 公司公告、声明、官网 | 写"公司称" |
| 媒体报道 | 记者核实过的报道 | 写"媒体报道"，注明媒体与日期 |
| 匿名舆情 | 帖子、员工爆料、匿名投诉 | 写"网络传言/匿名帖"，不得作为事实依据 |

### 4.2 双源

同一事件至少两个**独立**来源（不同 originGroupId）。同一新闻稿被多家转载只算一个源；公司声明与其转载也不算双源。只有一个源的事件，`incidents.status` 保留，但 `flags` 标 `attention` 并写"单源"。

### 4.3 时间与后续

每条事件必须写：发生时间、首次曝光时间、当事人回应时间（如有）、最新进展时间。只写曝光时间不写后续，视为不完整。

### 4.4 利益相关方

只记录**公开可见**的表态与可核事实（如集体投诉数量、供应商起诉、监管约谈）。不推断沉默方的态度，不把个别员工言论当公司立场。

### 4.5 字段填充示例（占位符，不是真实数据）

```jsonc
{
  "incidents": [
    {"date": "2025-04", "title": "某产品投诉集中出现", "summary": "投诉平台出现多条同类投诉",
     "sourceTier": "database", "status": "已回应", "note": "公司发布说明；已双源，另一源为媒体报道"}
  ],
  "sentiment": [
    {"period": "2025 上半年", "tone": "负面", "summary": "投诉与交付延期话题集中", "note": "样本 N 条，来源以投诉平台与行业媒体为主"}
  ],
  "stakeholders": [
    {"party": "供应商", "stance": "反对", "note": "公开报道称存在货款结算争议"}
  ]
}
```

## 5. 六态与边界

- `found`：原始页面可打开且与事件对应；
- `not_disclosed_after_search`：查过搜索、媒体、投诉平台、法院公告仍无；
- `lower_bound`：只知道"多条投诉"而无具体数量；
- `pending_dd`：需要公司提供投诉台账、和解协议、内部调查结论；
- `conflict`：公司与投诉方说法矛盾，保留两方陈述；
- `not_applicable`：无面向消费者的业务、无公开舆情；
- `not_reviewed`：本轮未查；
- `estimated`：仅允许用于"舆情热度/口碑倾向"等分析型判断，必须带 `derivation`；事件事实一律不得 estimated。

边界：不采集个人隐私与身份信息；不对个人进行人身评价；不做舆情处置建议；不把匿名帖当事实；不把"负面"写成"违法"。

## 6. 常见误判

1. 把匿名帖、员工爆料当事实。
2. 把单条投诉当系统性质量事故。
3. 把两家媒体转载同一稿件当双源。
4. 把旧闻当新闻（未核首发时间）。
5. 用情绪化词汇给公司定性（"黑心""骗局"）。
6. 忽略公司回应与后续处置。
7. 用搜索结果条数当舆情热度。
8. 把个别员工言论当公司立场。
9. 把已和解的纠纷继续写成"发酵中"。
10. 把媒体报道的"涉嫌"写成"已认定"。

## 7. 验收要点

- 证据：≥5 条；每个事件至少 1 条可打开的原始页面；
- 覆盖：负面事件、举报/投诉、利益相关方、整体口碑四类都有结论；
- 双源：主要事件有双源或明确标注"单源"；
- 必答：①时间窗内最主要的 3 个负面事件及后续；②是否有实名举报或监管立案；③公司是否回应；④员工与客户的主要不满点；⑤整体口碑趋势；
- 一致性：与 `legal.risk` 的诉讼事件一致；与 `org.people` 的关键人一致。

## 8. 与其他模块的关系

- 上游（硬）：`org.people`、`business.segment`；软引用 `legal.risk`；
- 下游：`red-flags`（舆情触发器）、`assessment-fit`（合作声誉风险）、`deliverable`（风险提示）；
- 不重复：诉讼与执行事实归 `legal.risk`；行政处罚归 `regulatory-compliance`；员工人数与社保归 `workforce`。

## 9. 交付前自检

- [ ] 每条事件有日期、来源、状态、后续
- [ ] 五级信息强度标注清楚
- [ ] 双源或"单源"标注到位
- [ ] 公司回应已记录（有则写，无则写"未见回应"）
- [ ] 没有情绪化定性
- [ ] 全文无 `stable`、`已审` 字样

## 10. 明确不覆盖

- 舆情处置与公关建议；
- 个人名誉、隐私与人身评价；
- 未公开的内部举报内容；
- 销量与品牌价值的量化评估；
- 对媒体报道真实性的独立调查（只记录与交叉，不定性）。
