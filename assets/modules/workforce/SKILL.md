# workforce · 组织、人力与用工

> 模块状态：**draft**。方法论未经金融专家评审，不得声称 `stable` 或"专家已审"。
> 输出底稿：`workforce.profile`（scope=company，cardinality=one，partitionKey=`_default`）。
> 一句话目标：用人数、结构、人效、社保与招聘五条线，判断这家公司的"人"是否撑得起它的收入与产能。

## 1. 回答什么问题

1. 现在有多少人？口径是期末在职、全年平均、合并还是母公司？
2. 人分布在哪些职能、学历、地域、产线上？研发占比多少？
3. 人均营收、人均净利、人均薪酬是多少，与自身历史比是升还是降？
4. 社保与公积金是否按实际人数、实际基数缴纳？有没有欠缴、稽核、补缴线索？
5. 在招什么岗位、在哪些城市、招了多久？扩张还是收缩？
6. 有没有劳动争议、集体欠薪、工伤、竞业限制纠纷？

## 2. 输入、前置与降级

| 关系 | 类型 | 说明 |
|---|---|---|
| 硬输入 | `company.identity` | 提供全称、代码、曾用名，用于检索消歧 |
| 软引用 | `financials.public` | 提供营业收入、应付职工薪酬、"支付给职工以及为职工支付的现金"，用于人效与人均薪酬 |
| 软引用 | `supply.capacity`（如已产出） | 产线/基地信息，用于解释人数变动 |

- 降级：无 `financials.public` 时，人效与人均薪酬写 `pending_dd`，不得用行业均值替代；人数与结构仍须完成。
- 分区：单一 artifact，`{{unit.partition}}` 恒为 `_default`。
- 回溯年限由 `{{params.yearsBack}}` 控制，默认 3 年。

## 3. 检索计划

### 3.1 来源优先级

| 序 | sourceTier | 典型来源 | 用途 | authority |
|---|---|---|---|---|
| 1 | announcement | 年报"员工情况"、ESG/社会责任报告、可转债/债券募集说明书 | 人数、结构、薪酬、社保披露 | A |
| 2 | company | 招股书"员工与社会保障"章节、官网"关于我们/团队" | 历史人数、劳务派遣、社保合规说明 | B |
| 3 | registry | 国家企业信用信息公示系统"企业年度报告"的社保信息栏 | 参保人数（五险分项） | B |
| 4 | regulator | 人社局/医保局/公积金中心公示、社保稽核公告、欠薪曝光 | 欠缴、稽核、处罚 | A |
| 5 | court | 中国裁判文书网（案由：劳动争议、追索劳动报酬、工伤保险待遇） | 劳资纠纷 | A |
| 6 | database | 招聘平台（BOSS 直聘、猎聘、智联、前程无忧）岗位快照 | 招聘趋势、地点、薪资带 | C |
| 7 | media | 权威媒体裁员/欠薪报道、员工评价社区 | 线索 | C–D |

### 3.4 必查库与必开页面

- 巨潮资讯网/交易所：最近 `{{params.yearsBack}}` 期年报"员工情况"；
- 国家企业信用信息公示系统：历年年报的"社保信息"（养老、医疗、失业、工伤、生育分项参保人数）；
- 招股说明书："员工及其社会保障"章节（含劳务派遣比例、社保缴纳比例、补缴风险提示）；
- 中国裁判文书网：以公司全称为当事人的劳动争议案件；
- 招聘平台：按公司名检索在招岗位，记录抓取日期与岗位数；
- 地方人社局/公积金中心：欠缴、稽核、行政处罚公示。

### 3.5 检索顺序与预算

1. 年报人数与结构（约 4 次）；
2. 工商年报社保信息（约 3 次）；
3. 人效与薪酬（复用 `financials.public`，约 2 次）；
4. 招聘快照（约 2 次）；
5. 劳动争议（约 2 次）。
上限见 `module.yaml` 的 `budget.toolCallsPerUnit`。

## 4. 字段与口径

| 字段 | 结构 | 定义 | 算 `found` | 算 `not_disclosed_after_search` |
|---|---|---|---|---|
| `data.headcount` | number | 在职员工总数 | 年报/招股书明确数字且给时点 | 只有"约""数百人"等模糊表述 |
| `data.structure[]` | `kind`/`count`/`pct` | 按职能、学历、地域或产线拆分 | 有分项数字或可算出的占比 | 只披露一个维度且无分项 |
| `data.socialInsurance` | number | 参保人数 | 工商年报社保栏或招股书明确数字 | 只有"依法缴纳"文字 |
| `data.employeeCost` | `amount`/`currency`/`unit`/`note` | 职工薪酬总额 | 年报"应付职工薪酬"本期增加或现金流量表项目 | 只有"人工成本"定性表述 |
| `data.hiring[]` | `role`/`location`/`count`/`note` | 在招岗位快照 | 招聘平台可见且在招 | 平台不可达或需登录 |
| `data.laborDisputes[]` | 自定义 | 劳动争议、欠薪、工伤 | 裁判文书/官方公示可读 | 同名或已下架 |

- 数值字段（`headcount`、`socialInsurance`、`employeeCost`）在 schema 中是数字/对象，**不承载六态**；六态写在对应的 claim 上，并在 `data.headcountNote`、`data.socialInsuranceNote` 这类同名 note 字段里写明口径与检索记录。
- 未知时不要填 0，也不要省略说明；填 note + claim(`not_disclosed_after_search`)。

### 4.1 口径专论：人数

至少区分四种口径：期末在职、全年平均、合并范围、母公司。年报"在职员工的数量合计"通常是期末、合并；工商年报"从业人数"常为申报口径，二者不可混用。写数字必须带"口径 + 时点"。

### 4.2 口径专论：社保

- 参保人数有时点是"期末"还是"全年"的差异；五险分项人数不同属正常（如工伤险覆盖劳务派遣）；
- 参保人数 < 在职员工数，可能是劳务派遣/外包/退休返聘/异地参保，也可能是未足额缴纳——只能写"需核"，不能直接定性；
- 缴费基数按最低基数申报是常见合规瑕疵，需要工资表才能判断，属 `pending_dd`。

### 4.3 口径专论：人效与人均薪酬

- 人均营收 = 营业收入 / 平均在职人数（口径须与营收口径一致：合并对合并）；
- 人均薪酬优先用"应付职工薪酬本期增加额 / 平均人数"；用"支付给职工以及为职工支付的现金"时须说明含社保与个税；
- 股权激励费用不计入"人均薪酬"的现金口径，需单列说明。

### 4.4 口径专论：招聘趋势

招聘平台岗位数是**快照**，不是招聘量。记录抓取日期、城市、岗位类别；只有连续多期快照才能谈"趋势"，单期只能谈"当前在招"。

### 4.5 口径专论：劳务派遣与外包

- 劳务派遣有比例上限（用工单位使用被派遣劳动者数量不得超过其用工总量的 10%），超标本身是合规风险，但需先确认分母口径；
- 劳务外包不算派遣，不占比例，但"假外包真派遣"是常见问题，只能写"需核外包合同与现场管理方式"；
- 年报"劳务外包"栏给的是外包工时或金额时，不能反推人数。

### 4.6 字段填充示例（占位符，不是真实数据）

```jsonc
{
  "headcount": 0,
  "headcountNote": "found；口径=期末在职、合并范围；时点=最近一期年报披露",
  "structure": [
    {"kind": "生产人员", "count": 0, "pct": 0},
    {"kind": "研发人员", "count": 0, "pct": 0}
  ],
  "socialInsurance": 0,
  "socialInsuranceNote": "found；工商年报社保栏，参保口径为期末，五险分项见 claims",
  "hiring": [{"role": "设备工程师", "location": "某市", "count": 0, "note": "抓取日期以 run 记录为准"}]
}
```

示例中的 0 只表示"位置占位"，实际提交必须是真实可核数字；查不到则删去数字并在 note 写六态。

## 5. 六态与边界

- `found`：有明确数字与口径；
- `not_disclosed_after_search`：查过年报、招股书、工商年报仍无；
- `lower_bound`：只给"不少于 N 人"或分项之和小于总额；
- `pending_dd`：需要工资表、社保缴费明细、劳务派遣协议；
- `conflict`：年报人数与工商年报从业人数差异大且无法解释，两个值都保留；
- `not_applicable`：无雇工的个体/壳主体；
- `not_reviewed`：本轮未查；
- `estimated`：仅允许用于"人效""人均薪酬"等分析型派生值，须带 `derivation`；人数与参保人数一律不得 estimated。

边界：不采集员工个人姓名、工号、薪酬明细、身份信息；不做"裁员传闻"的定性；不评价雇主品牌。

## 6. 常见误判

1. 把工商年报"从业人数"当成"在职员工数"（申报口径，可能含劳务派遣）。
2. 把母公司人数当合并人数（或反之），导致人效算错一倍。
3. 用"员工总数"减"参保人数"直接得出"未缴社保人数"（忽略派遣、外包、异地参保）。
4. 把招聘平台岗位数当成实际招聘人数或编制扩张。
5. 用单一年份的人均薪酬与同行比，忽略地区与岗位结构差异。
6. 把"研发人员"与"技术人员"混为一谈（前者是认定口径，后者是岗位分类）。
7. 跨年比较时未注意口径变化（如合并范围新增子公司）。
8. 把员工评价社区的帖子当成劳资纠纷事实。

## 7. 验收要点

- 证据：≥5 条；人数、社保、结构三类各至少 1 条 `supports`；
- 覆盖：人数、结构、社保、人效、招聘五项中至少四项有结论或六态说明；
- 交叉源：人数至少 2 源（年报 + 工商年报/招股书）；
- 必答：①在职人数与时点；②研发人员占比；③参保人数与在职人数差异及原因；④人均营收；⑤近一年在招岗位的主要方向；
- 一致性：`structure` 分项之和与 `headcount` 的偏差需在 note 说明；人数口径与 `financials.public` 的合并范围一致。

## 8. 与其他模块的关系

- 上游（硬）：`company.identity`；软引用 `financials.public`、`supply.capacity`；
- 下游：`assessment-fit`（人力是否支撑合作放量）、`red-flags`（社保/欠薪触发器）、`deliverable`；
- 不重复：职工薪酬的会计处理归 `financials.public`；安全培训与工伤事故归 `esg-ehs`；社保行政处罚归 `regulatory-compliance`。

## 10. 明确不覆盖

- 职工薪酬的会计科目处理与资本化（归 `financials.public`）；
- 安全生产事故与职业健康（归 `esg-ehs`）；
- 社保、欠薪的行政处罚（归 `regulatory-compliance`，本模块只留线索）；
- 组织架构图与汇报关系（除非公开披露，否则 `pending_dd`）；
- 员工满意度、雇主品牌与个人绩效评价。
